## What it's for

`git tag` puts a fixed name on a commit, `v1.1.0`, to mark a version. Unlike a branch, a tag doesn't move. The full manual: `git help tag`. The choice of the number, the GitHub release and the rest of the practice: [Versions and tags](/en/equipe/versions-et-tags/).

## The forms that matter

**`-a name -m "message"`**: an annotated tag, on the current commit or on the one you give. `git tag` alone lists, `-n` with the messages, and `--decorate` on `log` shows them in their place.

```console
$ git tag -a v1.1.0 -m "Version 1.1.0"

$ git tag -a v1.0.0 -m "Version 1.0.0" HEAD~2

$ git tag
v1.0.0
v1.1.0

$ git tag -n
v1.0.0          Version 1.0.0
v1.1.0          Version 1.1.0

$ git log --oneline --decorate -3
6226bbe (HEAD -> main, tag: v1.1.0, origin/main) feat: c
aaf484e fix: b
8952b33 (tag: v1.0.0) feat: a
```

**Annotated or lightweight**: without `-a`, the tag is only a pointer, without author, date or message. `cat-file -t` tells the difference. Lightweight for a marker of your own, annotated for a version.

```console
$ git tag brouillon

$ git cat-file -t v1.1.0
tag

$ git cat-file -t brouillon
commit

$ git tag -d brouillon
Deleted tag 'brouillon' (was 6226bbe)
```

**Filtering and sorting**: `-l` with a pattern, `--sort=-version:refname` in version number order, and not in alphabetical order where `v1.10.0` comes before `v1.2.0`.

```console
$ git tag -l 'v1.1*'
v1.1.0

$ git tag --sort=-version:refname
v1.1.0
v1.0.0
```

**Sending to the server**: `push` doesn't push tags. One by one, or all at once with `--tags`.

```console
$ git push origin v1.1.0
To github.com:equipe/projet.git
 * [new tag]         v1.1.0 -> v1.1.0

$ git push --tags
To github.com:equipe/projet.git
 * [new tag]         v1.0.0 -> v1.0.0

$ git ls-remote --tags origin
e8ed368f9e6ab0268871f7b5693505d95f659f49	refs/tags/v1.0.0
8952b33d4bb2fc8dd5d65355e72668b17d4ae56a	refs/tags/v1.0.0^{}
ac1d081a28a9f4839aad852f5ef453d03240fad1	refs/tags/v1.1.0
6226bbe0bf0e2ee29997b6ad79978e868e52e3c3	refs/tags/v1.1.0^{}
```

**Deleting**: locally, then on the server, in two separate commands. For a tag never published only; a published tag isn't withdrawn, you publish the next version.

```console
$ git tag -d v1.0.0
Deleted tag 'v1.0.0' (was e8ed368)

$ git push origin --delete v1.0.0
To github.com:equipe/projet.git
 - [deleted]         v1.0.0

$ git ls-remote --tags origin
ac1d081a28a9f4839aad852f5ef453d03240fad1	refs/tags/v1.1.0
6226bbe0bf0e2ee29997b6ad79978e868e52e3c3	refs/tags/v1.1.0^{}
```

**Reading a tag**: `show` gives the annotation then the commit, `describe` says which version a commit belongs to.

```console
$ git show --no-patch v1.1.0
tag v1.1.0
Tagger: Awa <awa@example.com>
Date:   Mon Oct 5 10:00:00 2026 +0000

Version 1.1.0

commit 6226bbe0bf0e2ee29997b6ad79978e868e52e3c3
Author: Awa <awa@example.com>
Date:   Mon Oct 5 10:00:00 2026 +0000

    feat: c

$ git describe --tags HEAD
v1.1.0
```

## Pitfalls

- **Forgetting to push the tag**: the machine has the version, not the server. `git config --global push.followTags true` pushes annotated tags along with the branch.
- **`--tags` pushes everything**, drafts and lightweight tags included. `git push origin v1.1.0` or `--follow-tags`, which takes only reachable annotated tags, are better.
- **Moving a published tag**: those who fetched it keep the old one. If the version is wrong, it's `v1.1.1`.
- **A tag deleted on the server stays on colleagues' machines** until `git fetch --prune --prune-tags`.
- **A branch rule doesn't protect tags**: on GitHub, a tag ruleset for `v*`: [Protecting the main branch](/en/equipe/proteger-la-branche-principale/).
