## What it's for

`git push` sends your commits to the server and moves the branch over there forward up to yours. It refuses if the server received in the meantime something you don't have: that's the guard rail that prevents overwriting other people's work, and the whole page revolves around it. The full manual: `git help push`.

## The forms that matter

**`git push -u origin branch`** for a branch's first push: it creates it on the server and sets the tracking link. Without `-u`, Git refuses and says what to do.

```console
$ git push
fatal: The current branch feature/recherche has no upstream branch.
To push the current branch and set the remote as upstream, use

    git push --set-upstream origin feature/recherche

To have this happen automatically for branches without a tracking
upstream, see 'push.autoSetupRemote' in 'git help config'.


$ git push -u origin feature/recherche
To github.com:equipe/projet.git
 * [new branch]      feature/recherche -> feature/recherche
branch 'feature/recherche' set up to track 'origin/feature/recherche'.
```

**`git push`** afterwards, without arguments: the tracking link says where to go.

```console
$ git push
To github.com:equipe/projet.git
   b9b596d..93460ed  feature/recherche -> feature/recherche
```

**Rejected, "fetch first"**: the server has a commit you don't have, here a colleague's on the same branch. `--force-with-lease` refuses too, "stale info": your copy of the server is out of date, forcing would overwrite their commit. The only way out is to fetch first, with `git pull --rebase`.

```console
$ git push
To github.com:equipe/projet.git
 ! [rejected]        feature/recherche -> feature/recherche (fetch first)
error: failed to push some refs to 'github.com:equipe/projet.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.

$ git push --force-with-lease
To github.com:equipe/projet.git
 ! [rejected]        feature/recherche -> feature/recherche (stale info)
error: failed to push some refs to 'github.com:equipe/projet.git'
```

**`--force-with-lease`** on your own branch, after rewriting it with an `--amend` or a rebase. A plain `push` is rejected, "non-fast-forward", because the server has the old version of the commit; `--force-with-lease` replaces it, because this time your copy of the server is up to date: nobody pushed in the meantime.

```console
$ git push
To github.com:equipe/projet.git
 ! [rejected]        feature/recherche -> feature/recherche (non-fast-forward)
error: failed to push some refs to 'github.com:equipe/projet.git'
hint: Updates were rejected because the tip of your current branch is behind
hint: its remote counterpart. If you want to integrate the remote changes,
hint: use 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.

$ git push --force-with-lease
To github.com:equipe/projet.git
 + dc812f2...bb388d8 feature/recherche -> feature/recherche (forced update)
```

**`git push origin --delete branch`** deletes a branch on the server. Yours stays.

```console
$ git push origin --delete feature/recherche
To github.com:equipe/projet.git
 - [deleted]         feature/recherche
```

**`push.autoSetupRemote`**: never `-u` again, a branch's first `push` sets the link on its own.

```console
$ git config --global push.autoSetupRemote true
```

## Pitfalls

- **Plain `--force`** overwrites without checking: if someone pushed in the meantime, their work disappears from the server. `--force-with-lease` refuses in that case, for a few more letters. On `main`, neither one nor the other: [Protecting the main branch](/en/equipe/proteger-la-branche-principale/).
- **The old commits are not lost** after a force push: they are in your reflog, and in that of the colleagues who had fetched them: [Finding a lost commit](/en/situations/reparer/retrouver-un-commit-perdu/).
- **"fetch first" and "non-fast-forward"** are the same situation, seen before and after the `fetch`: [My push is rejected, "rejected", "fetch first"](/en/situations/quotidien/push-refuse-fetch-first/).
- **`git push` doesn't push tags**: `git push origin v1.2.0`, or `--follow-tags`: [Versions and tags](/en/equipe/versions-et-tags/).
- **`git push origin main` from `feature/x`** doesn't push your branch: it pushes your local `main`. Without arguments, `push` sends the current branch to the one it tracks, and that's almost always what you want.
- **A `push` refused by GitHub with a `GH006` or `GH013` code** is not this situation: the branch is protected, and expects a pull request.
